Component Development Standards

Maintaining high code quality across distributed developer contributions requires structured engineering conventions. These guidelines guarantee consistency across the Axon UI codebase.

Naming Conventions

  • Components (PascalCase): React components must use PascalCase (e.g. DatePicker, AccordionPanel).
  • Hooks (camelCase): Hook files must start with the prefix use in camelCase (e.g. useFocusTrap, useOutsideClick).
  • CSS Classes (kebab-case): We follow **BEM (Block Element Modifier)** style naming rules using kebab-case:
    • .axon-button (Block: Component base)
    • .axon-button__icon (Element: Node nested inside button block)
    • .axon-button--primary (Modifier: Specific styling state variant)

Folder & File Conventions

We enforce a strict **co-location strategy**. All testing assets, styling rules, TypeScript definitions, and story playgrounds must exist in the component folder itself. This simplifies code deletion and local auditing.

Component Folder File Tree
components/
└── Menu/
    ├── Menu.tsx               # Primary React component source
    ├── Menu.types.ts          # TypeScript prop interfaces
    ├── Menu.styles.css        # Scoped CSS variable variables
    ├── Menu.test.tsx          # Component unit and regression tests
    ├── Menu.stories.tsx       # Storybook playground code
    └── index.ts               # Barrel export redirection

Prop Design Standards

When designing props interfaces, follow these conventions to build clean, intuitive APIs:

  1. Extend HTML Attributes: When wrapping native elements, always extend the native HTML type (e.g. React.InputHTMLAttributes<HTMLInputElement>). This ensures users can bind default input features (like onKeyDown, name, placeholder) without editing the library.
  2. Boolean Props: Use boolean flags only for binary state switches (e.g. isDisabled, isOpen). Avoid using booleans for style options (e.g. isPrimary, isSecondary)—use union type values instead.
  3. Variant Prop Union Types: Define style overrides as explicit union listings (e.g. variant: 'solid' | 'outline' | 'ghost') rather than using generic strings.

Composition Patterns vs. Giant Props

Avoid creating monolithic, bloated components with dozens of configuration props. Instead, leverage **sub-component composition** to allow customization:

Poor Practice: Giant Props
// Hard to scale, forces the component to manage layout details
<Card
  title="My Card"
  body="Description"
  buttonText="Submit"
  onButtonClick={handlePress}
  footerText="Copyright 2026"
/>
Good Practice: Component Composition
// Clean, flexible, lets developers structure layouts individually
<Card>
  <Card.Header>
    <Typography variant="h3">My Card</Typography>
  </Card.Header>
  <Card.Body>
    <Typography variant="body">Description</Typography>
  </Card.Body>
  <Card.Footer>
    <Button onClick={handlePress}>Submit</Button>
    <Typography variant="caption">Copyright 2026</Typography>
  </Card.Footer>
</Card>

Headless Component Strategy

To scale a component library across multiple styling systems, or support custom rendering layouts, separate component functionality from styling rules.

  • Logic Hooks (Headless): Keep keyboard listeners, click-outside toggles, and state machines in code-only hooks (e.g. useMenu).
  • Visual Wrappers (Styled): Keep styling rules in visual wrappers (e.g. Menu.tsx) that consume the state engine outputs from hooks.

Using this strategy, teams can build a different set of visual styles (e.g. using Tailwind or styled-components) while sharing the exact same interactive state engine.
