Testing Guide

A UI Component Library is a shared dependency that sits at the base of the enterprise tech stack. To prevent layout shifts and regressions in downstream products, we enforce a strict testing workflow.

Testing Strategy Matrix

Our testing strategy combines different levels of validation to catch functional, accessibility, and visual regressions before release:

Test Type Focus Area Target Tools
Unit Testing Isolated component states, hooks output, and utility values. Vitest, @testing-library/react-hooks
Integration Testing User events (clicks, input typing) and focus changes. Vitest, React Testing Library, @testing-library/user-event
Accessibility (a11y) Automated checks for screen reader landmarks, label links, and contrast ratios. Vitest, vitest-axe (axe-core wrapper)
Visual Regression Pixel-perfect rendering checks across themes and viewport sizes. Playwright, Chromatic, Storybook Test Runner
Snapshot Testing Locks DOM markup in place to flag unexpected HTML structure shifts. Vitest snapshots (toMatchInlineSnapshot)

Unit & Integration Testing

Unit and integration tests run inside an optimized JSDOM simulation environment using **Vitest** for speed.

Example: Testing Button States & Click Interactivity

Button.test.tsx
import { describe, test, expect, vi } from 'vitest';
import { render, screen } from '@testing-library/react';
import userEvent from '@testing-library/user-event';
import { Button } from './Button';

describe('Button Component', () => {
  test('renders children correctly', () => {
    render(<Button>Click Me</Button>);
    expect(screen.getByRole('button', { name: /click me/i })).toBeInTheDocument();
  });

  test('calls onClick handler when clicked', async () => {
    const handleClick = vi.fn();
    render(<Button onClick={handleClick}>Action</Button>);
    
    const button = screen.getByRole('button');
    await userEvent.click(button);
    
    expect(handleClick).toHaveBeenCalledTimes(1);
  });

  test('does not trigger onClick when disabled or loading', async () => {
    const handleClick = vi.fn();
    render(<Button onClick={handleClick} disabled>Disabled</Button>);
    
    const button = screen.getByRole('button');
    await userEvent.click(button);
    
    expect(handleClick).not.toHaveBeenCalled();
  });
});

Accessibility (a11y) Testing

Automated a11y tests catch common accessibility errors (like missing labels or unmapped labels) before manual QA checks. We run these checks using a Vitest wrapper for **axe-core**.

Example: Testing Accordion for a11y Violations

Accordion.a11y.test.tsx
import { describe, test, expect } from 'vitest';
import { render } from '@testing-library/react';
import { axe } from 'vitest-axe';
import { Accordion } from './Accordion';

const mockItems = [
  { id: '1', title: 'Header 1', content: 'Panel context 1' }
];

describe('Accordion Accessibility', () => {
  test('should have zero accessibility violations', async () => {
    const { container } = render(<Accordion items={mockItems} />);
    const results = await axe(container);
    
    expect(results).toHaveNoViolations();
  });
});

Visual Regression & Snapshot Testing

  • Visual Regression Testing: Run during CI pipelines using Chromatic. Playwright opens stories, grabs viewport images, and compares them pixel-by-pixel with baseline images.
  • Snapshot Testing: Keeps the component DOM structure locked in place. Only use snapshots when you want to guard against unexpected changes to a component's generated HTML output.
Snapshot Testing Trap

Avoid snapshot testing components that import third-party elements. If a third-party package modifies its internal tag attributes, your local snapshots will break, leading to false alarms in the build pipelines.
