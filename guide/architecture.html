Architecture Guide

An enterprise UI Component Library must be engineered with modularity, stability, and strict boundaries in mind. This page details the high-level code architecture and component dependencies of Axon UI.

High-Level Architecture

The library is structured as a collection of modular packages linked in a mono-repository. This configuration guarantees that structural components, visual tokens, and graphical assets remain separated, allowing custom clients to import only what they need.

Dependency Boundaries

Enforcing clean, unidirectional dependency limits is the cornerstone of avoiding architectural debt. We enforce the following limits:

  • Tokens (@axon/tokens): Must have zero runtime dependencies. It should only contain design tokens (variables) compiled into JSON, CSS custom properties, and static JS/TS assets.
  • Icons (@axon/icons): Depends on @axon/tokens only for token alignment. It holds visual icon assets.
  • React Code (@axon/react): Depends on @axon/tokens and @axon/icons. It must not import application-level state management tools, and holds peer-dependency definitions for react and react-dom.
Anti-Pattern Warning

Never import code from a workspace package that resides higher in the stack. For example, a file inside packages/tokens must never import files from packages/react. Circular dependencies will break bundling, tree-shaking, and incremental builds.

Component Lifecycle

Axon UI components follow a strict rendering and execution lifecycle to maintain performance and prevent hydration mismatches during Server-Side Rendering (SSR):

sequenceDiagram participant C as Component (React) participant D as DOM (Browser) participant P as Provider (Theme) C->>P: Read current theme tokens P-->>C: Inject CSS custom properties C->>C: Calculate state & variant classes C->>D: Initial Paint (A11y/ARIA bindings active) C->>D: Mount hooks (Focus trapping, keyboard listeners active) Note right of C: Active Lifecycle State D->>C: User triggers action (Unmount) C->>D: Remove event listeners & release focus

To support SSR frameworks (like Next.js), components must remain isomorphic. They perform layout arithmetic (like bounding rect calculations) only inside layout effects or after mounting in client-side hooks, ensuring they render correctly on the server without crashing.

Build Pipeline

The library build pipeline uses a modern, fast compile stack to process tokens, icons, and React TSX into highly optimized bundles:

  1. Token Compilation: @axon/tokens compiles JSON source files into target styles formats (CSS Variables, Sass, and JS modules) using Style Dictionary or a custom node build script.
  2. Icon Bundling: Raw SVGs are run through SVGO (to clean markup and strip hardcoded fill properties) and compiled into functional React component wrappers using SVGR.
  3. React Compilation: React TypeScript code is bundled using Vite (powered by esbuild and Rollup plugins) to export dual-format modules (ESM for modern bundlers, and CommonJS for legacy systems), outputting type declaration files (.d.ts) using vite-plugin-dts.
Build Configuration

We use **Tree Shaking** configuration in package.json by specifying "sideEffects": ["*.css"]. This tells bundlers like Webpack and Vite that our JavaScript modules are side-effect-free, enabling the compiler to strip unused components from the application bundle.
